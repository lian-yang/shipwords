# Job submission and settlement contract

Only jobs created with the server-owned `inputJson._verifiedBilling: true` snapshot use verified settlement. Other sites retain their existing behavior. The shared API enables this snapshot from the server-side model's `verifiedBilling` field; clients cannot set it through request parameters. Site-specific job creators must write the snapshot themselves.

Local adapter configuration and request serialization are checked before the claim, so a confirmed local error can be refunded without contacting the provider. A verified job then atomically claims its first upstream operation before dispatch, and records each normal and repair operation's exact input and idempotency key before dispatch. Replays of an active operation use that stored input and key. A cancellation refunds only before the claim. To avoid untracked provider charges, prep hedge copies are disabled for verified jobs; legacy jobs retain their existing hedge behavior. A verified effect that relies on hedge acceleration therefore has lower availability/performance until separately tracked hedge operations are implemented.

A verified failed job keeps credits and guest quota until every recorded upstream operation is terminal and its provider bill is settled. Zero total charges trigger an idempotent credit refund and guest-quota release; a positive charge keeps the debit; unavailable, malformed, or pending bills remain pending. Job reads and site cron retry `billing_pending` and `billing_refunding`, and the refund ledger entry must exist before the task is marked refunded. Failed-job email is sent by the workflow only after the refund is complete; pending and billed failures do not receive the old "credits returned" email. A later cron settlement currently does not send a delayed email.

A persisted pending submission can be replayed only while its workflow remains active. After local failure or timeout, reconciliation never submits it because doing so could create a new charge. If Yir does not return an ID before the local job ends, the task stays pending and the operator can inspect the idempotency key using `pendingSubmissionKeys` and contact Yir. Yir's job read does not provide a machine-verifiable key-to-job association: no manual ID attachment or manual zero-charge override is available. There is currently no automatic end-to-end resolution for that case; it requires a separately designed evidence-backed support process. Do not treat a missing Yir log as proof of no charge.

`PublicJob.settlement` is `not_applicable`, `pending`, `refunded`, or `charged`, and `refunded` follows successful ledger settlement. Status remains unchanged. Sites enabling verified settlement must render these values and not claim every failure was refunded. No schema migration is required.
